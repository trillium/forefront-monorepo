# Backend Decisions

Design decisions for the Forefront backend. One row per decision. Mirrors the
iOS repo's `Docs/DECISIONS.md` style; these are the **server-side** choices.

| ID   | Decision | Alternative | Why |
| ---- | -------- | ----------- | --- |
| B-01 | **Chat + deck state persists in `bun:sqlite`** at a file DB (`.data/forefront.db`, gitignored, `FOREFRONT_DB_PATH`-overridable). The Next server runs under the **Bun runtime** (`bun --bun next dev/start`) so the driver resolves. | Keep everything in-memory like the deck fixture; or add an external DB dependency (Postgres/SQLite npm pkg); or `node:sqlite`. | The chat contract needs durable threads, monotonic per-thread cursors, `clientMessageId` idempotency, and unread tracking — in-memory loses all of it on restart mid-test. `bun:sqlite` is built into the runtime, so this adds **zero** dependencies and gives real SQL for cursor/dedup queries. The store is a single lib seam (`lib/store.ts`) so a hosted DB can drop in behind the same functions later. **Load-bearing detail:** `next dev/start` normally spawn a **Node** server, where `bun:sqlite` does not exist. So `package.json` runs Next via `bun --bun`, which forces the Bun runtime for route handlers. `next build` still runs under Node, but the driver is `require`d **lazily** inside `openDatabase` (never at module import), so the build — which only collects page data, never opens a DB — stays green. A `node:sqlite` swap is a one-seam change if the Bun-runtime requirement ever becomes inconvenient. |
| B-02 | **Two credentials: device Bearer = the human, a separate agent key = the agent.** `validateBearer` (existing) authorizes reads + `user` messages; a new `validateAgent` (env `FOREFRONT_AGENT_TOKEN`) authorizes `/agent/*` — authoring `agent`/`system` messages, curating the deck, reading the human read-back inbox. | One shared token for phone + agent. | The producer surface must be strictly more privileged than the consumer surface: a compromised phone token must **not** be able to forge `agent` messages or reorder the deck. Separate secrets make that a hard boundary, not a convention. The device token literally cannot reach any `/agent/*` route. |
| B-03 | **Cursors are opaque monotonic integers rendered as strings**, one sequence shared across all messages (global autoincrement `seq`). `since=<cursor>` returns rows with `seq > cursor`. | Per-thread sequences; timestamp cursors. | The contract treats cursors as opaque (§9, §11) and the client never parses them. A single global `seq` gives a total order that works for *both* the per-thread consumer fetch (§9) and the cross-thread agent inbox (`GET /agent/inbox`) with one mechanism. Deck version reuses the same idea: bump on any card mutation so the client refetches. |
| B-04 | **APNs *sending* is out of scope; actionable-push records are persisted and exposed via `GET /agent/pushes`.** Enqueued whenever an agent authors a `reminder`/`question` with `push: true`. | Wire real APNs now. | Real APNs needs a signed key + cert + the `apns` topic and a production entitlement — none of which exist in a fixture backend. The contract (§11) says the client already handles receipt; the gap here is purely the *delivery* transport. Persisting the record makes the intent observable and testable, and is the exact seam a real APNs sender slots into. Documented in `BACKEND_SERVER.md` § APNs gap. |
| B-05 | **Deck cards curated in the store take over `getDeck()`; the static fixtures are the fallback when the store is empty.** Any card mutation bumps the deck version. | Replace fixtures outright; keep two parallel deck sources. | Preserves the existing device-testing flow (empty store → same three demo cards the app already renders) while making the deck agent-curatable through `/agent/cards`. `lib/deck.ts` stays the single seam the contract §2/§3 routes read, exactly as its header promised ("replace this body with a query"). |
